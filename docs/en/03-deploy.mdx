## Choose a Deployment

- **Azure:** use the existing [`terraform/`](https://github.com/f5-sales-demo/traffic-generator/tree/main/terraform) root and the Azure procedure below.
- **AWS:** use the independent [`terraform/aws/`](https://github.com/f5-sales-demo/traffic-generator/tree/main/terraform/aws) root and its [operator README](https://github.com/f5-sales-demo/traffic-generator/blob/main/terraform/aws/README.md).

Do not copy state, variable files, plans, lock files, or access instructions between these roots.

## AWS: Source and Runtime Inputs

Before planning, authenticate profile `280469140135_Users` and verify that it resolves to account `280469140135` in `us-east-1`. The AWS Terraform guards also validate the target domain. Authentication failure is a hard stop.

Set every required plan-time input using values obtained through the approved discovery and release process:
the exact AMI ID, instance type, 40-character source commit, deployment-manifest version and digest,
pinned Node 22 archive URL and SHA-256, pinned Chrome for Testing archive URL and SHA-256,
`operator_ssh_cidr`, and `ssh_public_key_path`. Never guess an image or artifact digest and never
commit credentials, key material, or local variable files.

The currently observed jumpbox public address is `142.127.218.190/32`; revalidate it immediately before every plan or apply because it is not permanent. On `robin@192.168.2.240`, the untracked public key path may be `/home/robin/.ssh/id_ed25519.pub`. Terraform reads that public key, while its private counterpart remains outside configuration and state.

The worker clones the exact source commit and verifies runtime archives before installation. Client-Side Defense browser scenarios run with headed Chrome under Xvfb.

They capture a sanitized screenshot after every primitive step and a final screenshot, plus a sanitized execution receipt outside Git. Successful execution and screenshots do not guarantee that F5 Distributed Cloud produced a detection; correlate the run window with tenant telemetry.

Headed Chrome and screenshot validation are AWS-runtime operations only. The normal developer command,
`node --test tests/csd-violations.test.mjs`, executes contract tests without launching a browser and
prints an explicit AWS-only skip reason. During AWS provisioning, `csd-worker-health.service` must
pass the gated browser integration against the deployed source commit, Chrome, Playwright, Xvfb
display, status identity, and runtime output directory before the worker is healthy.

## AWS: Plan and Apply

Run Terraform only from `terraform/aws/`. Its S3 backend uses bucket `terraform-tfstate-xc`, key `f5-sales-demo/traffic-generator-aws.tfstate`, region `us-east-1`, native state locking, and encryption. It is independent of Azure state.

1. Confirm AWS authentication and the guarded account, profile, primary region, replication region, and target domain.
2. On the jumpbox, revalidate its current public IPv4 and set `operator_ssh_cidr` to that exact `/32`; do not assume the documented example is still current.
3. Confirm `ssh_public_key_path` names an existing untracked public key file and contains no private key material.
4. Initialize the AWS root and review the generated dependency lock file.
5. Validate the configuration and create a saved plan.
6. Inspect the saved plan for the public-subnet EC2 worker, direct primary-ENI Elastic IP, restricted SSH, deny-all default security group, public route, service endpoints, encrypted runtime and VPC Flow Logs, EventBridge notifications on all four S3 buckets, primary and replica server access logging, KMS-encrypted/versioned source and replica buckets, and SSE-S3 terminal log sinks in each region.
7. Confirm the plan contains no NAT Gateway, private worker subnet, separate Elastic IP association resource, broad SSH ingress, automatic public-IP assignment, committed key material, or broad Checkov skip.
8. Review S3 lifecycle, replica-region KMS and replication IAM permissions, the narrow AWS-required SSE-S3 sink exemptions, plus ongoing CloudWatch, KMS, access-log, replication-transfer, and replica-storage costs.
9. Obtain explicit operator approval for that exact saved plan before applying it.
10. Apply only the reviewed plan; do not replace it with an unreviewed plan at apply time.
11. Use the `ssh_command` output for direct administration. Retain Systems Manager Session Manager and Run Command for recovery and constrained scenario execution.

After apply, verify SSH from the authorized jumpbox, Systems Manager connectivity, cloud-init/runtime
status, exact checked-out source commit, runtime provenance, service health, evidence upload, EventBridge
notification configuration on all four buckets, VPC Flow Log delivery, and S3 access-log delivery in both
regions. Then verify required source object versions report completed cross-region replication and use the
replica KMS key; replication is asynchronous and source upload success alone is insufficient. Run the
approved scenario and correlate its timestamps with F5 Distributed Cloud telemetry. Follow the AWS README
for guarded destroy; retained source, replica, primary-log, and replica-log versions must be handled
deliberately.

## Azure: Clone and Configure

All Azure Terraform files remain in the [`terraform/`](https://github.com/f5-sales-demo/traffic-generator/tree/main/terraform) directory. Clone the repository and deploy directly:

```bash
git clone https://github.com/f5-sales-demo/traffic-generator.git
cd traffic-generator/terraform
cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars with your Azure subscription ID and target FQDN
```

## Azure Terraform Configuration

### Terraform File Structure

The terraform directory contains 9 files following the Demo Resource Standard:

- `versions.tf` -- Terraform and provider version constraints (azurerm ~> 4.0, azuread ~> 3.0)
- `providers.tf` -- Azure RM and Azure AD provider configuration
- `data.tf` -- Azure AD data sources for deployer auto-resolution
- `locals.tf` -- Deployer resolution, Azure Cloud Adoption Framework resource naming, standard tags
- `main.tf` -- Resource group (named `rg-traffic-generator-{environment}-{deployer}`)
- `variables.tf` -- All input variables (2 required, 9 optional) with deployer auto-resolution via Azure AD
- `network.tf` -- VNet (10.201.0.0/16), subnet, public IP, NSG (port 22 SSH), NIC
- `vm.tf` -- Ubuntu 24.04 VM with cloud-init via templatefile()
- `outputs.tf` -- 17 outputs: 15 standard outputs shared by all demo resources (deployer, public_ip, private_ip, ssh_command, resource_group_name, vm_name, nsg_name, vnet_name, subnet_id, component, environment, resource_group_id, vm_id, nsg_id, location) plus 2 component-specific outputs (target_fqdn, status_check)

### Cloud-Init Provisioning

`cloud-init.yaml` is the production-validated configuration verified under 48+ hours of continuous load testing including 4 rounds of origin torture testing. It uses a helper library with retry logic, progress logging to `/var/log/cloud-init-progress.log`, 9 provisioning phases, and conditional status reporting (ready/degraded in `status.json`). It provisions:

- **Kernel tuning** -- `somaxconn=131072`, `tcp_max_tw_buckets=4000000`, `tcp_fin_timeout=5`, 64 MiB socket buffers, `file-max=4194304`
- **NIC optimization** -- RPS/RFS across all cores, maximized ring buffers via ethtool, THP=always
- **APT packages** -- nikto, nmap, masscan, sqlmap, hydra, medusa, ncrack, tshark, hping3, tcpdump, netcat, ngrep, iperf3, mtr, sslscan, socat, dirb, whatweb, wrk, hey, vegeta, ethtool
- **GitHub Releases** -- nuclei, dalfox, ffuf, gobuster, feroxbuster, subfinder, httpx, amass
- **Python packages** -- mitmproxy, sslyze, dnsrecon, fierce, theHarvester, playwright, scapy, impacket, arjun
- **Node.js 20.x** -- Puppeteer with stealth plugin for bot simulation
- **Browser automation** -- Playwright Chromium for headless browser testing
- **Git clones** -- testssl.sh, recon-ng, spiderfoot, SecLists, waf-bypass, PayloadsAllTheThings
- **Suite deployment** -- 19 traffic suites cloned from this repository to `/opt/traffic-generator/suites/`
- **Config file** -- `config.env` with `TARGET_FQDN`, `TARGET_ORIGIN_IP`, and `CRAPI_PORT`

The cloud-init uses Terraform template variables: `${target_fqdn}`, `${target_origin_ip}`, and `${tool_tier}`. Shell variables like `$NPROC` are escaped as `$$NPROC` in the Terraform templatefile.

## VM Sizing

The F-series compute-optimized VMs are recommended for this CPU-bound traffic generation workload. The cloud-init kernel tuning and tool concurrency scale automatically with vCPU count.

| VM SKU           | vCPU | RAM    | Network   | Use Case               |
| ---------------- | ---- | ------ | --------- | ---------------------- |
| Standard_F4s_v2  | 4    | 8 GiB  | 10 Gbps   | Light lab/demo         |
| Standard_F8s_v2  | 8    | 16 GiB | 12.5 Gbps | Standard demos         |
| Standard_F16s_v2 | 16   | 32 GiB | 12.5 Gbps | Load testing (default) |
| Standard_F32s_v2 | 32   | 64 GiB | 16 Gbps   | Heavy benchmarking     |
| Standard_D16s_v3 | 16   | 64 GiB | 12.5 Gbps | RAM-heavy workloads    |

:::tip
F16s_v2 was validated as the optimal price-performance option by A/B/C/D benchmark testing against CDN F16s_v2 and F32s_v2 targets. See [benchmarks/](https://github.com/f5-sales-demo/traffic-generator/tree/main/benchmarks) for full results.
:::

## Azure Post-Deploy Verification

Cloud-init provisioning takes **15-20 minutes for standard tier** and **approximately 25 minutes for full tier**. The VM is accessible via SSH immediately, but tools are still being installed until cloud-init completes.

### Wait for Cloud-Init

SSH into the VM and wait for provisioning to finish:

```bash
ssh azureuser@$(terraform output -raw public_ip)

cloud-init status --wait
```

Expected output when complete:

```text
status: done
```

### Check Status File

The cloud-init script writes a status file upon completion:

```bash
cat /opt/traffic-generator/status.json
```

Expected output:

```json
{
  "status": "ready",
  "tier": "standard",
  "target_fqdn": "demo.example.com",
  "completed": "2026-04-25T14:30:00Z",
  "tools_installed": true
}
```

### Verify Critical Tools

Run a verification loop to confirm each critical tool is available on PATH:

```bash
for tool in nikto sqlmap nuclei dalfox ffuf gobuster feroxbuster nmap masscan \
  hydra medusa ncrack sslscan tshark hping3 mitmproxy sslyze subfinder httpx \
  amass arjun mtr whatweb dirb socat netcat ngrep iperf3 whois dig wrk hey; do
  if command -v "$tool" > /dev/null 2>&1; then
    echo "OK: $tool"
  else
    echo "MISSING: $tool"
  fi
done
```

### Verify Suite Runner

Confirm the runner and suites are installed:

```bash
ls /opt/traffic-generator/suites/runner.sh
ls /opt/traffic-generator/suites/*/

/opt/traffic-generator/suites/runner.sh web-app-attacks --dry-run
```

## Wiring from Upstream Components

The traffic generator targets an F5 XC HTTP load balancer that fronts the origin server. Deploy the origin server first, configure F5 XC, then set `target_fqdn` to the load balancer's FQDN:

```bash
# After deploying origin-server and creating an F5 XC HTTP load balancer:
cat > terraform.tfvars <<EOF
subscription_id  = "SUBSCRIPTION_ID"
target_fqdn      = "your-xc-load-balancer.example.com"
target_origin_ip = "$(cd ../../origin-server/terraform && terraform output -raw public_ip)"
EOF
```

| Required Variable  | Source                           | Description                                                 |
| ------------------ | -------------------------------- | ----------------------------------------------------------- |
| `target_fqdn`      | F5 XC console                    | FQDN of the HTTP load balancer protecting the origin server |
| `target_origin_ip` | Origin server `public_ip` output | Direct origin IP for bypass testing (optional)              |
