## Azure catalog operation

The supported discovery command is `bash suites/runner.sh <SUITE> --dry-run` from the source root, or the same command under `/opt/traffic-generator/current` after installation. It reads the explicit catalog only. Select `catalog` for all 164 scenarios. There is no non-dry-run `runner.sh` execution mode or `config.env` target override in this interface.

```bash
bash suites/runner.sh catalog --dry-run
bash suites/runner.sh dvwa-payloads --dry-run
```

On the owned installed generator, use the supervised control interface:

```bash
sudo tgen-control status
sudo tgen-control stop
sudo tgen-control run-once
sudo tgen-control start
```

| Verb | Behavior |
| --- | --- |
| `status` | Read private runtime status plus actual service active/enabled state |
| `stop` | Disable and stop `tgen-continuous.service` |
| `run-once` | Reject active continuous execution, check readiness, then run one complete catalog pass; incomplete acceptance returns nonzero |
| `start` | Check readiness, then enable/start continuous supervision |

Set `TGEN_ROOT` or `CATALOG_CONFIG` only for an explicitly owned alternate installation. Default private configuration is `/opt/traffic-generator/catalog-config.json`; runtime/source use `current` and the venv supplied by the immutable installer. Root privileges are required for namespace/systemd operation. Do not launch individual attack or benchmark scripts around the pacing boundary.

## Configuration and prerequisites

`suites/catalog-config.example.json` documents the structured input contract. Materialize real approved
domains, source commit and archive SHA-256 privately; zero/example values are symbolic, not a working
deployment. Keep approved credentials/session exports out of docs. `catalog_readiness.py --config` checks
required binaries/assets, browser, certificates, application routes and fixtures before execution. Missing
tools or auth fail prerequisites instead of substituting dummy tokens, sessions or responses.

The shared HTTP boundary fixes 200 aggregate requests/sec: 180 benign (90 per approved domain, rotated across
nine application paths) plus a shared 20 scenario/filler budget. Every scanner/browser/subprocess/nested load
request crosses the namespace pacing proxy. Filler is attributed separately and cannot satisfy a meaningful
scenario action. Connection attempts are capped at 20/sec with up to 20 held slow connections; those caps are
separate from HTTP accounting. The per-scenario deadline is 900 seconds. Exact native phase configuration,
connection behavior and resource samples remain required even when pacing limits throughput.

## Receipts, restoration and attribution

Launch/action receipts, actual native reports, source/binary/adapter digests, process cleanup and browser
screenshots remain private. The runtime heartbeat records exact installed provenance, scenario/pass inventory,
measured rates and failures. Fixture mutation journals capture baseline/native postconditions and exact
restoration; preserve failure and interruption receipts. crAPI OTP uses a distinct synthetic mutation actor
and real recipient-bound MIME mail. Recurring signup/vehicle/reset ownership integration remains open.

Functional acceptance is separate from request dispatch. Native response content/status, tool phase completion
and observed process cleanup must match the declared contract. Missing contracts, skipped prerequisites, tool
errors, timeout, transport failure and cancellation cannot pass. Expected native application rejection remains
distinct from a mitigation candidate; correlated WAAP control evidence lives in a separate receipt.
`csd_enabled=false`: browser library execution and cleanup prove display activity only.

Detailed runtime evidence is bounded to seven days or 10 GiB, evicting oldest completed runs. Keep
state/credentials/mail and screenshots private. See [Continuous catalog](../continuous-catalog/), [current
tasks](../continuous-catalog-tasks/) and [native audit](../native-tool-remediation/). Complete exact-source
catalog passes, sustained rates, recovery and showcase clean rebuild remain open.

cd terraform/aws

$(terraform output -raw ssh_command)

## AWS Unattended CSD Hydration

`terraform/aws` owns the CSD worker's runtime configuration. `continuous_enabled` is a boolean
defaulting to `true` and exposed by the same-named output. Cloud-init writes exactly one
`CONTINUOUS_ENABLED=1|0` field into `/etc/traffic-generator/runtime.env`, stops scheduling before
installation, verifies pinned source/dependencies/dispatcher presence, starts Xvfb and bounded headed
health, requires `ready`, then enables/starts `csd-continuous.timer` when enabled. Disabled hydration
still installs and validates the units and dispatcher but stops/disables automatic launches.

Publish and review the implementation before choosing deployment inputs: use the exact published
merge SHA containing `continuous.mjs` and compatible `run.sh`/`run.mjs`, and derive the canonical
`scenarios.mjs` digest at that same immutable commit. Keep the reviewed manifest version. Never use
a moving branch, guessed future SHA, old one-shot pin, or uncommitted source injected into user data.
The symbolic placeholders in `terraform.tfvars.example` are intentionally not deployable values.
A user-data change retains worker replacement behavior; use the reviewed saved-plan and separate
termination-protection procedure in the [AWS stack guide](https://github.com/f5-sales-demo/traffic-generator/blob/main/terraform/aws/README.md).

Each root-managed service firing invokes `continuous.mjs tick` through pinned Node and executes at
most one of the existing eleven scenarios, or one due frozen-upload retry without Chrome. Names and
order come directly from `SCENARIO_NAMES` in `scenarios.mjs`; terminal decisions advance the cursor
and wrap into another cycle. `completedCycles` does not mean eleven detections or successful uploads.
The generic catalog scheduler excludes CSD and is not a second CSD execution owner.

The enabled timer persists across reboot without rerunning cloud-init. It fires after 30 seconds at
boot and 15 seconds after the prior oneshot becomes inactive, with 1-second accuracy and no replay
of missed firings. Dispatch requires network-online and healthy Xvfb/headed Chrome. Cleanup,
backoff, lock contention, and reboot introduce gaps: recurring traffic is not literally zero downtime.

### Sanitized Status and Temporary Pause

Run on the AWS worker:

```bash
sudo /opt/node/bin/node \
  /opt/traffic-generator/source/suites/csd-violations/continuous.mjs status
systemctl is-enabled csd-continuous.timer
systemctl is-active csd-continuous.timer csd-continuous.service
```

An inactive oneshot between ticks is normal. Sanitized status includes cursor, completed cycles,
attempted/browser-passed/committed/failed/timeout/interrupted counters, heartbeat, current run/scenario,
last outcome, backoff schedule, and pending uploads, not credentials, raw identities, or error bodies.
Root persists atomic private state at `/opt/traffic-generator/runtime/continuous/state.json`. Persistent
fatal blocks survive reboot; do not delete state to hide a failure or assume restart fixes its cause.

Before deliberate SSM traffic or UAT, stop the timer and let the current run drain within its
1,100-second service budget. Verify the service is inactive and the common lock is free:

```bash
sudo systemctl stop csd-continuous.timer
systemctl is-active csd-continuous.service
sudo flock -n /run/lock/csd-traffic-generator.lock /usr/bin/true
# If deliberate cancellation is necessary instead of draining:
sudo systemctl stop csd-continuous.service
```

After cancellation, verify owned-child cleanup and interrupted/pending evidence before proceeding.
`run.sh` alone acquires the shared nonblocking lock for both normal and upload-retry work; do not
unlink it or add nested locks. Reboot tmpfiles recreates it as root:tgen `0660`. A temporary timer stop
does not survive reboot: disable it for reboot-spanning maintenance, or deploy the reviewed
`continuous_enabled = false` setting. Record/reconcile any operational override; do not permanently
hand-edit the Terraform-owned environment. Resume only after maintenance, healthy runtime, and no
manual lock holder, with the reviewed enabled configuration:

```bash
sudo systemctl enable --now csd-continuous.timer
```

Do not invoke internal `tick` as an operator start command. **Dedicated Page Tamper UAT must inhibit
and drain recurrence for its entire quiet/baseline/canary/recovery window.** No automatic CSD-controller
reservation integration is provided, and no Page Tamper baseline, canary, or header matrix is scheduled.

### Bounded Retries, Cleanup, and Retention

Scenario/browser execution has a 900-second budget, finalization 120 seconds, and owned-child cleanup
30 seconds. Systemd bounds service start/stop to 1,100/45 seconds with cgroup containment; health
start/stop is bounded to 120/30 seconds. These limits do not depend on SSM command timeouts.
Transient work allows at most three total attempts with 30/60/120-second backoff steps capped at 300
seconds; exhaustion records failure and advances to avoid starving other scenarios. Busy lock retries
consume neither cursor nor attempt budget. Fatal configuration/provenance/target/integrity/authentication
failures block further launches persistently.

At most 32 pending uploads are recorded; each frozen upload has at most three total retry attempts,
each bounded to 120 seconds. Retry-only ticks never rerun Chrome. Exhausted pending evidence stays
visible/frozen; queue or disk limits block new work instead of deleting it. The run-root
`execution-result.json` (schema version 1), outside the frozen scenario directory, distinguishes browser
exit, upload exit/commit, outcome, failure category, and signal. Missing/inconsistent results are failures.

Only completed committed directories are eligible for oldest-first pruning after seven days or above
5 GiB of local detail. New work is rejected below 1 GiB free space; pending evidence has a 2 GiB cap.
Active and pending evidence is not silently pruned. Local append-open logs rotate daily or at 10 MiB
with seven rotations, compression/delayed compression, and copytruncate. Diagnose disk blocks and
preserve evidence before authorized cleanup; never remove active or pending runs to bypass bounds.

Acceptance on each approved fresh deployment requires committed hash-validated evidence for all
eleven names over two cycles, monotonic counters, bounded disk, no owned-child leaks, and controlled
reboot recurrence. Ready health, active units, browser success, and committed uploads do not guarantee
CSD detection. The dated proof below records one deployment's measured execution and evidence results;
it does not replace acceptance checks on another deployment.

#### Next-Day Observation Is Not a Manual Start

For an enabled deployment, use the sanitized status and unit checks above to observe readiness,
timer enablement/activity, persisted monotonic counters, current work, fatal blocks, and pending uploads.
An inactive oneshot between firings is normal. Compare counters across a measured interval; do not
manually launch a scenario or invoke `tick` just to make the system appear active. Investigate unhealthy
runtime, stalled counters, or queued evidence before claiming continued operation. The dated reboot
and no-op observations are not a next-day measurement or a guarantee of future uninterrupted traffic.

#### Paused UAT Is a Separate Operating Mode

Dedicated Page Tamper UAT must stop scheduling and drain active work before its quiet, baseline,
canary, and recovery window, and keep recurrence inhibited throughout that window. Follow the pause,
lock, cancellation-evidence, and reboot-spanning maintenance guidance above. Resume the reviewed
enabled timer only after UAT and runtime health checks. Autonomous scenario cycling neither reserves
that quiet window nor substitutes for its separate detection and recovery evidence.

## AWS Systems Manager Run Flow

Use the non-sensitive `ssm_document_name` and `instance_id` outputs from `terraform/aws`. The
document accepts one case-sensitive `Scenario` string from the 11-name allowlist and uses the
configured authorized target. It does not accept shell fragments, credentials, synthetic values,
or arbitrary URLs.

```bash
cd terraform/aws
COMMAND_DOCUMENT=$(terraform output -raw ssm_document_name)
INSTANCE_ID=$(terraform output -raw instance_id)

COMMAND_ID=$(aws ssm send-command \
  --profile "$AWS_PROFILE" \
  --region us-east-1 \
  --document-name "${COMMAND_DOCUMENT}" \
  --instance-ids "${INSTANCE_ID}" \
  --parameters 'Scenario=login-credential-skimmer' \
  --query 'Command.CommandId' \
  --output text)
```

For a deliberate manual pass after pausing/draining recurrence, submit the 11 scenarios serially
because all entrypoints share the same lock. Retain each command ID and poll for at most 1,860
seconds per command. This covers the document's 1,800-second command timeout plus a bounded
status-propagation margin; actual execution remains bounded by the wrapper. The default
`command-executed` waiter can expire after roughly 100 seconds while a valid scenario is still running.
Manual submission is optional, not the normal hydration/start path.

```bash
for scenario in \
  login-credential-skimmer \
  registration-harvester \
  payment-overlay-card-skimmer \
  obfuscated-loader \
  multi-cdn-injection \
  tag-manager-hijack \
  multi-channel-exfiltration \
  high-volume-domain-exfiltration \
  form-overlay \
  keylogger-simulation \
  maximum-detection
do
  command_id=$(aws ssm send-command \
    --profile "$AWS_PROFILE" \
    --region us-east-1 \
    --document-name "${COMMAND_DOCUMENT}" \
    --instance-ids "${INSTANCE_ID}" \
    --parameters "Scenario=${scenario}" \
    --query 'Command.CommandId' \
    --output text)
  printf '%s %s\n' "${scenario}" "${command_id}"

  deadline=$((SECONDS + 1860))
  while :; do
    status=$(aws ssm get-command-invocation \
      --profile "$AWS_PROFILE" \
      --region us-east-1 \
      --command-id "${command_id}" \
      --instance-id "${INSTANCE_ID}" \
      --query Status --output text)
    case "${status}" in
      Success) break ;;
      Pending|InProgress|Delayed)
        if (( SECONDS >= deadline )); then
          printf 'Timed out polling %s after 1860 seconds\n' "${command_id}" >&2
          exit 1
        fi
        sleep 15
        ;;
      Cancelled|Cancelling|TimedOut|Failed)
        printf 'Command %s ended with status %s\n' "${command_id}" "${status}" >&2
        exit 1
        ;;
      *)
        printf 'Unexpected command status %s for %s\n' "${status}" "${command_id}" >&2
        exit 1
        ;;
    esac
  done
done
```

Inspect each invocation by command ID. The worker rejects overlapping runs with a lock, creates a unique run ID, and prints only sanitized status. Retry interrupted work only after determining whether the previous run is active, complete, failed, or still uploading.

### AWS Evidence Contract

Each invocation writes evidence under
`/opt/traffic-generator/runtime/results/<run-id>/<scenario>/` and uploads that directory to
`s3://<evidence_bucket_name>/runs/<run-id>/<scenario>/`. The runner receives the run root, appends
the allowlisted scenario exactly once, and rejects unsafe run identifiers; therefore local relative
paths and receipt object keys map one-to-one without scenario double nesting. Every setup, action,
assertion, and explicit cleanup manifest step has an ordinal, scenario, and step-name PNG; each scenario
also has an ordinal `final` PNG. The full suite produces 45 step PNGs plus 11 final PNGs, for 56 total.
Missing step, cleanup, or final screenshots make the scenario fail.

Each scenario's last manifest operation is `cleanup`. It removes run-scoped scripts, links, images,
overlays, listeners, timers, and synthetic controls as applicable, then asserts zero remaining artifacts,
populated controls, sensitive display values, and tracked timers, plus no attached key listener. The runner
screenshots that asserted cleanup state. Its `finally` cleanup is a safety net and runs before the separate
final screenshot. Browser-observed network request objects remain sanitized receipt evidence and do not
represent DOM artifacts.

`receipt.json` contains `schemaVersion`, `runId`, its own S3 `objectKey`, sanitized target protocol
and host, `startedAt`, `completedAt`, aggregate `counts`, `discarded`, `discardReasons`, `scenarios`,
`cleanup`, and a detection caveat. Scenario entries contain timestamps, status, steps, sanitized network
outcomes, instrumentation counts, and a final screenshot. Step entries contain timestamps, operation,
status, assertion checks, optional navigation status or structured evidence, and screenshot metadata.
Screenshot metadata contains capture status, relative path, exact object key, `uploadStatus`, SHA-256,
and masked-input count.

The suite captures each PNG to a temporary file and atomically renames it. Screenshot
`uploadStatus` remains `pending` in the immutable `receipt.json`; it describes the captured object's
state at evidence freeze time and is never rewritten after hashing. Finalization writes
`run-status.json`, `upload-manifest.json`, and `SHA256SUMS`, validates every local hash, uploads every
ordinary object, then uploads the manifest and checksum set. Every upload supplies user metadata
`sha256=<local-digest>` and deliberately omits SSE flags because the private evidence bucket applies
its default customer-managed KMS key.

`upload-commit.json` is the single authoritative commit object and is uploaded last. It contains the
exact SHA-256 digests of `upload-manifest.json` and `SHA256SUMS` and records `status: committed`.
Consumers must treat all other uploaded objects as pending unless that exact commit object exists and
its referenced hashes validate. The commit file and local `.finalization-failed.json` marker are not
members of `SHA256SUMS`, so recording success or failure never mutates hashed evidence.

Any ordinary-object, metadata, checksum, or commit upload failure leaves the local failure marker and
exits nonzero. Retry from the worker without rerunning Chrome:

```bash
sudo -u tgen env RUNTIME_ENV=/etc/traffic-generator/runtime.env \
  /bin/bash /opt/traffic-generator/source/suites/csd-violations/run.sh \
  --retry-upload "$EVIDENCE_RUN_DIR"
```

Retry revalidates the frozen local checksum set and exact run/scenario key prefix. For every expected
key it calls `s3api head-object`: HTTP 404/Not Found means the object is missing and may be uploaded;
authorization, transport, and other errors fail closed. An existing object is skipped only when its
case-normalized `Metadata.sha256` value exactly matches the frozen local digest. Missing checksum
metadata or a mismatch fails rather than overwriting a versioned key. Zero-byte files use the same
SHA-256 metadata contract. This also makes partial retries and an already committed retry idempotent:
matching objects, including `upload-commit.json`, are not uploaded again, while the commit remains last.
Before any tenant correlation, retrieve `upload-commit.json` from that exact prefix, require
`status: committed` and its exact expected object key, validate its recorded `upload-manifest.json` and
`SHA256SUMS` digests, and then validate the checksum set. Retrieve evidence through authenticated S3
or Systems Manager access; never create persistent public URLs. The bucket is private, encrypted,
versioned, lifecycle-managed, and configured with `force_destroy = false`.

The evidence bucket also emits object events to EventBridge and records S3 server access requests in a
dedicated same-region sink. Each source object version is eligible for asynchronous cross-region replication.
Before treating a replica as durable evidence, inspect the source version's replication status and require
completion; the successful upload and `upload-commit.json` contract do not prove that replication has finished.
Source, replica, and access-log versions remain private and lifecycle-managed, and each may independently block
guarded teardown until its retention decision and purge approval are complete.

Receipts omit form and key values, cookies, authorization material, storage values, headers,
request/response bodies, and sensitive URL components. Screenshots must not be treated as safe
merely because receipts are sanitized; inspect them before customer use.

### Browser and Detection Boundaries

A passed browser receipt means the headed Chrome/Xvfb setup, action, assertion, and explicit cleanup
steps executed, cleanup assertions passed, every step and final screenshot was captured, and browser/context
cleanup completed without recorded errors. The Systems Manager command succeeds only when the browser run
and subsequent S3 upload both succeed. Neither result proves that F5 Distributed Cloud generated a CSD detection.

Record browser-observed sensor and `__imp_apg__/api/dip` requests separately from optional read-only tenant correlation. Report tenant correlation as `OBSERVED`, `NOT_OBSERVED`, `PENDING`, or `ERROR`; pending or absent telemetry does not turn a successful browser run into a failure.

After the exact-prefix `upload-commit.json` and its referenced evidence digests validate, convert receipt
`startedAt` and `completedAt` ISO timestamps to epoch seconds. The operator must then use the structured
`xcsh_api` method/path/params/payload workflow in
[Integrate](../07-integrate/#operator-side-post-receipt-correlation):
`GET /api/shape/csd/namespaces/{namespace}/detected_domains`,
`POST /api/shape/csd/namespaces/{namespace}/scripts` with snake_case `start_time` and `end_time`, and
`GET /api/shape/csd/namespaces/{namespace}/formFields` with those query parameters. Compare exact
receipt-derived reviewed hosts only for `detected_domains` and `scripts`. Treat `formFields` as an optional
aggregate receipt-window observation: record only count and `OBSERVED` or `PENDING` classification, never
attribution to a specific generated field identifier. Store normalized endpoint results separately; never
rewrite the browser receipt or change its result.
